# UX

How products and pages should work for the people using them. The UI framework (`06-ui-framework.md`) says which component to use; this file says how to shape the experience around it: who it is for, how flows run, how trust is earned, and when work is done.

## UX principles

1. **Make verification legible.** Anyone should be able to tell, in one glance, what is verified, by which program, until when, and what that means.
2. **Always show the next step.** Every screen answers "what do I do now?" Dead ends get an action, empty states get a first step, errors get a fix.
3. **Respect people's time.** Ask only for what is needed, never twice. Save progress automatically. Long work can stop and resume.
4. **Problems are ours to explain.** When something fails, the system says what happened and how to recover. People are never blamed.
5. **One way to do one thing.** The same task uses the same pattern in every program and product, so learning it once is enough.
6. **Accessible by default.** WCAG 2.2 AA is the floor, not a feature (see `08-accessibility.md`).

## Who we design for

| Audience | Main jobs | Context | Design for |
|---|---|---|---|
| Shoppers | Check if a product is verified, find verified products, understand what a seal means | Phone, in store, one hand, poor signal, seconds to spare | Speed, large targets, scan-first, plain answers, works offline where possible |
| Brands and manufacturers | Enroll products, submit documents, track review, renew, use the seal correctly | Desktop, deep work, many products, deadlines | Save and resume, bulk actions, clear status and dates, no surprises |
| Technical Administrators (TAs) | Review submissions across programs, request information, decide | Desktop, all day, high volume | Density, keyboard shortcuts, queues, side-by-side documents, nothing lost |
| Staff | Run programs, report, support partners | Desktop, many tools | Consistent shell, search everywhere, exportable data |
| Members (Collective) | Join, register for events, take part in campaigns, renew | Phone and desktop, occasional visits | Short flows, clear benefits, reminders |
| Funders, press, policy audiences | Understand the organization, find evidence, give | Desktop, reading | Clear structure, sourced claims, simple giving |

## Information architecture

- Organize by the person's task, not the org chart. "Find verified products", not "Program services".
- Each program site has the same top-level shape where it applies: Find products, For brands, The standard, About, plus a clear sign-in for participants.
- House-level navigation lists the three programs as equals, in the fixed order from `01-brand-architecture.md`.
- Records have one canonical URL. Shareable links open the same view for everyone with access.
- Search is available on every app screen, and finds products, brands, companies and documents by name or code.
- Keep hierarchy to three levels or fewer. Use filters for everything else.

## Core flows

### Check a product (shopper)

1. Scan a barcode or search by name.
2. See the result: product name, image, and status badge for each program, with the date verified.
3. Read what the verification means in one sentence, with a link to learn more.
4. If not verified, see verified alternatives in the same category.

Rules: result within 2 seconds on a mobile connection; manual entry is always available; a scan result is information, never shown as a verification unless the record says so.

### Enroll a product (brand)

1. Company details, filled once and reused.
2. Add products, singly or in bulk from a spreadsheet.
3. Upload documents, with accepted types and limits shown up front.
4. Review everything on one page.
5. Submit for review, then see the timeline and what happens next.

Rules: `Stepper` with save on every step; Back never loses data; partial submissions can be resumed from email; every request for more information names the exact document needed.

### Review a submission (TA)

1. Open the queue, sorted by due date.
2. Open a submission in a `Sheet` alongside the queue.
3. Check documents side by side with the standard's requirements.
4. Request information, approve, or decline, with a reason.
5. The brand is notified; the queue moves to the next item.

Rules: keyboard shortcuts for queue actions; decisions require a reason; every change is recorded in the timeline with who and when.

### Renew verification (brand)

1. Reminder at 90, 30 and 7 days before expiry, by email and in the app.
2. Confirm what has not changed; update only what has.
3. Submit; status shows "Renewal in review" while the current verification stays valid.

Rules: never let a verification lapse silently; show the expiry date wherever status appears.

### Join the Collective (member)

1. See what membership includes and costs.
2. Enter details and pay in one short form.
3. Confirmation with the first thing to do as a member.

Rules: three steps or fewer; the signature moment may mark "Welcome, member".

### Give (donor)

1. Choose an amount, with a plain line on what it funds.
2. Pay with a saved method, wallet or card.
3. Thank you, with a receipt by email.

Rules: no account required; monthly giving is an option, not the default; no pre-checked add-ons.

## Speed and feedback

| Time | What people perceive | What to show |
|---|---|---|
| Under 100ms | Instant | Nothing extra. Respond to the action directly |
| 100ms to 1s | A short pause | Button loading state; no skeleton under 300ms |
| 1s to 10s | Waiting | Skeleton for content, progress for known work, and what is happening |
| Over 10s | A task | Move it to the background, show progress, notify when done |

- Optimistic updates for small, reversible actions (rename, archive), with Undo.
- Never lose input on an error or a timeout. Keep the form filled and show what to fix.

## Trust and verification

- Show the source and date for every status: "Verified by Non-GMO Project · Mar 4, 2026".
- Explain each status in plain words on first encounter and on hover or tap ("What does this mean?").
- Never show a seal on a record that is not verified today (see `04-logos-and-marks.md`).
- Make it easy to report a problem with a product listing.
- Data collected from shoppers is the minimum needed, with a plain-language reason. Analytics respect Do Not Track and consent choices.

## Mobile and in-store

- Design for one hand and a thumb: primary actions in reach at the bottom, targets of 44px or more.
- Assume a weak connection. Cache recent results; show what was last loaded and when.
- Barcode scanning opens fast, works in poor light, and always offers manual entry.
- No horizontal scrolling at 320px, except data tables, which scroll inside their container.

## Notifications and email

| Kind | Channel | Rule |
|---|---|---|
| Action needed (documents requested, renewal due) | Email and in-app | Say what is needed, by when, and link straight to it |
| Status change (verified, declined, lapsed) | Email and in-app | One message per change, with the reason and next step |
| Confirmation (submitted, registered, donated) | Email | Immediately, with a reference number |
| Digest (weekly activity) | Email, opt-in | Off by default |
| Marketing and campaigns | Email, opt-in | Separate from service email; one-click unsubscribe |

Subject lines say the thing: "Documents needed for Heritage Rolled Oats by Oct 20". Every email comes from the program the person deals with.

## Research and measurement

| When | Method |
|---|---|
| Before building a new flow | Talk to five people who do the job today |
| Before release | Moderated usability test with five participants, including at least one assistive technology user |
| After release | Task success, time on task, drop-off per step, support tickets by topic |
| Quarterly | Review the top support questions; fix the cause, not the help article |

## UX definition of done

- The flow has been walked through with the jobs table above, for every audience it serves.
- Every screen has loading, empty, error and success states.
- Every action has feedback within 100ms.
- No dead ends: every state offers a next step.
- It works with a keyboard alone, with a screen reader, at 200% zoom and at 320px wide.
- Status shows program, label, icon and date.
- Copy follows `10-writing.md`.
- Data entered once is never asked for again in the same flow.
- Someone outside the team has tried it.

## Rules for Claude Code

- Before building a flow, name the audience and job from the table above, and say which core flow it follows or extends.
- Follow the core flow steps and rules when building any of those flows. If a requirement conflicts, flag it rather than silently changing the flow.
- Build every state in the definition of done, not just the happy path.
- Never add a step, field or confirmation that the flow does not need.
